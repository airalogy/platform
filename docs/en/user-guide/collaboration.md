# Collaboration

Collaboration in Platform follows the ownership hierarchy of Lab, Project, Protocol, and Record. Interface visibility helps users understand their current scope, while the API remains responsible for enforcing access.

## Work in the correct scope

- Use a Lab for long-lived membership and governance.
- Use a Project for a defined research objective or collaboration boundary.
- Keep Protocols in the Project that owns their scientific maintenance.
- Store Records under the Protocol and Project that own the work, rather than moving files through personal accounts.

## Roles

Lab Owners control the Lab’s highest-level settings and ownership actions. Lab Managers handle delegated administration. Members work within resources made available to them. Projects and structured Labs can add more specific roles and grants.

Having permission to view a parent resource does not imply permission to edit every child. Likewise, a hidden button is not proof that an operation is forbidden; the backend evaluates the effective role and scope for each protected action.

## Invite and hand off responsibly

Before inviting someone, confirm their identity, the minimum role they need, and the intended Project or organizational scope. Avoid granting Lab-wide management access for a task that only requires one Project.

For hand-offs:

1. Confirm all relevant Protocol versions and Records are stored in the shared scope.
2. Document pending work and known data-quality issues.
3. Transfer ownership or management through supported controls.
4. Verify the recipient can access the required resources before removing the previous maintainer.

## Links and public resources

Copying a Platform URL does not change the resource’s access rules. A recipient without effective access will not receive the protected content. Public Projects or Hub content should contain only material approved for public release.
