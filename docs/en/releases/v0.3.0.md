# Airalogy Platform v0.3.0

This release improves Protocol authoring, portable downloads and guided Record imports. The product and included API, Web, Instrument Interface, Gateway and Compute Runner versions move together to 0.3.0.

## Main changes

- Download a CSV template for the exact current Protocol, inspect field requirements, validate without creating Records, then explicitly confirm the import. Confirmations recheck data, permissions and preview freshness.
- Match CSV/TSV headers to Protocol field IDs; reject unknown or duplicate columns, spreadsheet error values and invalid data with grouped, bilingual feedback. UTF-8 BOM is supported. The importer does not guess aliases, repair scientific values or silently omit failed rows.
- Run declared client-side Assigners in Record forms through the published AIMD runtime. Preserve automatic, manual and first-run scheduling, validate mixed client/server dependency graphs, stop failed dependents and prevent submission of pending or failed calculations.
- Prefer client-side Assigners for appropriate simple calculations in AI-assisted Protocol generation and editing through published Masterbrain 0.13.0. External services, privileged operations and heavy computations remain server-side Python; AI output remains an editable draft.
- Download either a validated `.aira` archive or ZIP source package for an authorized, exact stored Protocol version. Exports omit database Records, environment secrets and executor caches. Existing ZIP integrations remain available.

## Upgrade and recovery

There are no database migrations after v0.2.0: the target revision remains `0075_legacy_file_metadata`. Verify the actual source revision rather than assuming it from the application version. Older deployments must follow the [v0.2.0 migration guidance](./v0.2.0.md).

Upgrade API and Web together and use the exact release manifest and immutable executor image. The API and isolated executor require the same Airalogy version; the executor also mounts the shared Assigner validation helper from the matching API release. Do not mix an old host with new mounted execution code. Keep external PostgreSQL and object storage unchanged.

The API pins Masterbrain 0.13.0. A separately deployed Masterbrain service must also support the client-first request contract before enabling that path; upgrading Platform does not automatically upgrade an independent service.

Before cutover, verify the recovery point and retain the previous application, configuration and web assets. Rehearse the release with isolated data and no production AI, notification or instrument credentials. Announce any write pause, verify release identity, and test Protocol save, Record submission, template preview/confirmation and both download formats using synthetic assets before declaring acceptance.

Application rollback does not require a schema downgrade from v0.3.0 to v0.2.0. However, older clients do not support the newly introduced client-side calculations: pause writes, assess newly created Protocols and Records, and retain their source and values before rollback. Do not blindly restore an old database and lose post-cutover writes. See the [release and deployment policy](../release-and-deployment-identity.md).

## Boundaries

Client-side calculations run in interactive Record forms, not CSV/API imports; imports must supply required derived values. The CSV template does not replace Protocol validation or domain review. This release does not introduce arbitrary old-table mapping, automatically correct clinical data, or validate scientific conclusions. Live model quality and real-instrument qualification require separate acceptance.
