# 自托管运维

本节面向实例运维人员。Platform 当前支持 Community 部署画像和面向生产的单实验室画像。应选择与实际安装方式匹配的部署指南，不要混用不同画像中的零散配置。

## 选择部署路径

- [Community Edition](../community-edition)：公开多 Lab 产品与本地优先默认设置。
- [单实验室部署](../single-lab-deployment)：成套生产服务、首次初始化、安全配置、校验和运维命令。
- [自托管架构](../architecture/self-hosted-architecture)：较大规模安装的服务与存储边界。

客户特有的主机名、账号、拓扑、SLA、支持工单和交付记录应保存在客户私有运维系统中，不得写入本公开文档。

## 部署

1. 选择干净、已提交的 Platform 修订或不可变发布清单。
2. 分别生成应用、加密、数据库、存储、内部 API 和初始管理员密钥。
3. 配置公开站点地址、部署模式、文档画像、存储、身份方式以及所需 AI 提供方。
4. 构建或拉取同时标有 Platform 版本与不可变 Git SHA 的镜像。
5. 对外提供服务前运行部署校验和数据库迁移。
6. 验证同一域名下的 `/api`、对象存储代理、Platform SPA 和 `/docs/`。

生产环境不得使用示例密钥。每次部署应记录版本、Git SHA、镜像摘要、数据库 revision、部署 ID 和配置变更记录。

## 升级

升级前阅读中英文更新日志和发布清单，并备份数据库、对象存储、配置以及必需的本地 Protocol 数据。所有组件应来自同一发布身份；先完成预检，再执行一次数据库迁移。

升级后验证登录、实例状态、Lab/Project/Protocol/Record 核心路径、上传下载、后台任务、内置文档，以及已配置的 AI 或执行器路径。验收完成前保留上一组不可变镜像和经过测试的恢复点。除非发布说明明确支持，不应假设数据库可以安全降级。

## 备份

一套可恢复的备份至少包括：

- 事务一致的 PostgreSQL 备份；
- MinIO 或外部对象存储中的对象及 bucket 元数据；
- 通过获准密钥管理流程备份的部署配置和密钥；
- 持久 Protocol/执行器数据以及发布与部署元数据；
- 恢复 DNS、TLS 和外部集成所需的说明。

备份介质应加密并限制访问，至少一份副本应位于主故障域之外，同时监控定时任务结果。应用层 Record 导出不能替代实例备份。

## 恢复

应在隔离环境中定期演练。把数据库和对象存储恢复到兼容时间点，使用匹配的配置和镜像版本，并只按该版本说明执行迁移。重新开放实例前核对文件解析、资源数量、近期 Record、访问规则和后台任务。

恢复点目标和恢复时间目标应由服务运营方与使用机构共同确定。从未完成恢复演练的备份，不能充分证明系统可恢复。

## 日常运维

- 监控服务健康、磁盘容量、数据库增长、对象存储、证书有效期和备份完成情况。
- 按制度保留 API、代理和审计日志，不记录可能包含密码或未公开数据的请求体。
- 通过计划变更轮换密钥，并验证所有依赖服务。
- 求助时生成脱敏支持包，不要在公开 issue 中写入客户身份或密钥。
- 使用[发布与部署身份](../release-and-deployment-identity)证明实际运行版本。

Platform Web 构建产物中的 `/docs/` 与应用使用同一源码修订构建。它属于公开产品信息；Platform 内的导航可见性不是保密边界。
