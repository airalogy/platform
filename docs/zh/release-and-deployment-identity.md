# 发布与部署身份

Airalogy Platform 将一次可部署产品标识为一个不可拆分的发布集合，而不是单独记录 Web 或 API 的版本号。

## 身份层级

| 层级 | 字段 | 用途 |
| --- | --- | --- |
| 产品版本 | `PLATFORM_VERSION` | 面向用户和发布说明的 SemVer |
| 源码身份 | Git Tag + 40 位 Git SHA | 精确回到可复现源码 |
| 发布身份 | `release-manifest.json` 的 SHA-256 | 绑定 API、Web、Protocol Executor、PostgreSQL 镜像及 Alembic revision |
| 部署身份 | `AIRALOGY_DEPLOYMENT_ID` | 标识一个安装实例，不携带客户语义 |

`AIRALOGY_DEPLOYMENT_ID` 是形如 `dep_<32 位随机十六进制数>` 的不透明标识。不要把客户名、Lab 名、域名、地址或合同号写进该字段。商业部署方可在自己的私有台账中建立“部署 ID → 客户与运维信息”的映射，该映射不属于本公开仓库。

Platform 不会默认将部署身份、客户信息或运行状态回传给 Airalogy。如需远程支持，由部署管理员显式生成并交付脱敏支持包。

## 正式发布

`VERSION` 是产品版本的唯一源。正式发布时：

1. 根据兼容性选择 SemVer，同步 `VERSION`、API、Web、Compute Runner、Instrument Gateway、Instrument Interface package 和根 workspace 版本。
2. 将中英文 Changelog 的 `Unreleased` 内容移入对应版本节。
3. 在已验证且干净的提交上创建 annotated tag `v<version>` 并推送。
4. Release workflow 运行后端、前端、Instrument Gateway、部署和发布检查，构建多架构镜像和同版本 Compute Runner、Gateway wheel/源码包，生成 SBOM 与 provenance，并组装不可变发布包。打包前对准确镜像集合执行账号权限、备份恢复及同版本升级回滚演练；测试配置、备份与状态留在包外，非预期文件或符号链接会阻止打包。
5. 正式部署使用 `镜像:版本@sha256:摘要`，不使用 `latest` 作为唯一身份。

科研设备主机应安装同一 GitHub Release 附带的 Gateway 包，在加入本地硬件适配器前核验其发布来源。

首版功能与验收边界见 [v0.1.0 发布概览](./releases/v0.1.0.md)。

源码 checkout 仍可用于本地开发和评估，但会标记 `BUILD_DIRTY` 且不具备正式发布清单的认证语义。

生成发布清单需要 Node.js 和 Python 3.11+。标准库 AST 读取器识别带类型标注及普通的 Alembic 字面量声明，不执行迁移模块；检查继承关系、缺失父版本、重复版本和循环后才选择唯一最新版本。非字面量声明或 `depends_on` 关系需要明确扩展工具支持，否则阻止发布而非静默忽略。

官方 `ghcr.io/airalogy/airalogy-engine:0.16.0` 镜像同时支持 `linux/amd64` 和 `linux/arm64`。Platform 固定其不可变 SHA-256 manifest 摘要，而不依赖 `latest`，因此两种架构都会解析到同一个已验证的发布身份。

## 生产故障与补丁发布

本节是维护者执行规范，不代表所有检查已自动化。核心原则：**故障恢复与功能升级分开。**

| 变更类型 | 推荐交付方式 |
| --- | --- |
| 兼容性的产品代码修复 | 回归测试、发布补丁版本，再部署经过验证的产物 |
| 配置、证书或缺少匹配镜像 | 修复环境、验证服务并记录运维变更，不必自动提升产品版本 |
| 数据库结构或数据迁移 | 版本化发布，附兼容性评估、迁移演练与数据恢复方案 |
| 必须立即恢复的严重故障 | 优先回退到已知可用且兼容的版本；经明确授权的最小应急修复只作为临时措施 |

例如，缺少 Protocol Executor 镜像，可以补齐与当前运行版本匹配的镜像恢复服务；完善产品启动检查和报错信息，则作为独立代码修复发布。不要为恢复这个故障顺带引入大量功能与数据库迁移。

### 补丁处理闭环

1. 记录部署版本、SHA、产物摘要、数据库 revision、影响及脱敏诊断，先分类再修改。
2. 如果开发分支已积累新功能，从线上实际部署版本创建修复分支，例如 `codex/hotfix-executor-startup`，不夹带未发布功能。仅纳入必要修复、回归测试和中英文发布说明，并将修复同步回开发分支。
3. 兼容性修复使用补丁版本，例如 `0.2.0 → 0.2.1`；按真实兼容性选择版本，而非把所有紧急变更都称为补丁。遵循前文正式发布流程，同步组件版本及锁文件。已发布的 Tag 和产物不可覆盖。
4. 先运行针对性回归，再运行受影响的集成、权限及必要发布检查。本地 hook 用于提前反馈，不能替代云端 CI 与发布检查；不得跳过失败项强行发布。
5. 在隔离环境验证准确的发布产物；涉及迁移时，演练线上实际版本到目标版本的升级。同版本升级测试不等于旧生产数据库已经验证。切换前记录备份和恢复证据。
6. 安排必要的停写窗口，取得最终可用恢复点，部署同一份已验证产物；核对版本、健康状态、错误日志以及保存 Protocol、提交 Record 等关键任务。使用专门测试资产，不修改用户科研数据。
7. 记录结果、剩余风险及回退处置后关闭故障。应急服务器修改必须先补齐源码、测试、文档及可复现部署。发布成功不等于部署成功，健康检查通过也不等于原始业务任务已恢复。

### 备份与回退门槛

- 云端副本或多可用区冗余不等于历史恢复能力。核对实际备份策略、最近成功备份、保留期、可恢复时间范围、恢复权限，以及成功恢复的证据。对象存储还需核对版本历史或独立备份及生命周期规则。
- 已验证的云端恢复点可以满足要求，不必每次部署都再做第二套全量备份。跨较大迁移或尚未验证云端恢复能力时，保留专门的升级前导出/备份并演练恢复。同机备份便于回退，但不属于独立灾备。
- 覆盖数据库、被引用文件、配置和匹配的应用产物；说明跨存储一致性和停写策略，不能将不同时间的在线快照直接视作一个一致恢复点。
- 明确旧应用能否使用迁移后的数据库；不兼容时，不能只回退镜像。写明恢复到新数据库等已验证步骤、预计恢复时间，以及切换后新增写入如何保留或处理。不得自动覆盖生产库或丢弃新增数据。
- 保留现有云数据库和对象存储，除非另有经过规划的基础设施替换。应用升级不代表允许数据库引擎降级，或用部署包默认服务替换外部存储。

### 私有运维变更记录

每次故障或部署保留一份受限记录：负责人及批准、影响及原因、变更前后版本/SHA/产物摘要/数据库版本、变更分类及代码修复、验证证据、备份时间与恢复演练、维护停写安排、回退触发条件与步骤、上线后检查及后续负责人。生产地址、凭证、数据、备份路径和未脱敏日志不得进入公开 Issue、发布说明或本仓库。公开 Changelog 描述产品修复，不披露部署拓扑。

## 部署命令与支持资料

正式发布包解压后，复制并填写 `.env`，然后执行：

```bash
./platformctl preflight
./platformctl install
./platformctl status
```

API 的 `GET /system/version` 返回产品版本、Tag、Git SHA、构建时间、dirty 状态、发布清单摘要、Alembic revision 和不透明部署 ID。`platformctl status` 会将运行中的 API 与发布清单重新比对。

```bash
./platformctl support-bundle
```

支持包只包含版本身份、不透明的核心镜像 ID/摘要、数据库 revision 和服务健康状态。它明确排除镜像仓库名、`.env`、密钥、日志、数据库、Records、附件、用户身份和客户名。该文件仍应作为运维资料限制访问。

`AIRALOGY_STATE_DIR` 持久保存当前发布、历次安装/升级/回滚事件、发布清单快照和失败恢复依据，不保存密钥或客户业务信息。
