# 实验室管理

本指南面向 Lab Owner 和 Manager，说明日常管理选择；真正的安全边界仍由后端访问模型提供。完整角色、授权、继承和审计模型见[访问控制参考](../access-control)。

## 成员与角色

添加成员前应核对身份和实际范围，并授予能完成工作的最小角色：

- **Owner** 控制 Lab 所有权、破坏性 Lab 操作和最高层级设置，应严格限制人数。
- **Manager** 承担被委派的管理工作，但不因此成为数据在法律或机构层面的所有者。
- **Member** 通过 Project 角色和 Lab 内的明确授权参与工作。

移除成员或降低角色前，应先转交其管理的资源和未完成责任。原记录人离开 Lab，不应成为删除共享研究数据的理由。

## Project 与组织访问

特定研究边界优先使用 Project 成员关系。结构化 Lab 可以通过组织单元和限定范围的授权表达真实团队，而不必赋予全 Lab 管理权。只有在子资源确实应跟随上级访问模型时，才保持继承开启。

建议定期检查：

- Owner 与 Manager；
- 已过期或撤销的授权；
- 公开访问设置；
- 使用例外继承规则的 Project 或 Protocol；
- 已不再需要访问的成员。

如果界面提供“有效访问”和审计历史，应以它们为准，不要只根据单一角色标签推断权限。

## 数据归属

研究数据应按适用协议和机构制度归属于 Lab 或组织，而不是某个浏览器会话或个人导出文件。Protocol、Record、文件和修订历史应留在承担所有权的工作空间中。Lab 应明确谁能批准公开、导出数据、删除资源和从备份恢复。

导出只是受控副本。导出行为不会自动转移数据所有权，也不会降低保密义务。重要导出应记录申请人、范围和去向。

## Lab 设置

应把 ID 视为长期标识，把名称与描述视为可编辑标签。修改公开范围、默认角色、组织结构或删除设置前，先评估对现有 Project 和链接的影响。

在单实验室部署中，固定 Lab 和默认 Project 的变化需要与实例运维人员协调。部分设置来自部署配置，需要经过验证的配置变更或镜像重建，不能只在界面中修改。

## 管理检查清单

1. 至少保留一个经过确认的 Owner 账号，并保护其恢复路径。
2. 按固定周期复核 Manager 和外部协作者。
3. 确认敏感 Project 没有继承非预期的公开访问。
4. 分别测试受控导出与运维备份。
5. 在适当的审计或机构系统中记录重要成员、访问和删除决定。
