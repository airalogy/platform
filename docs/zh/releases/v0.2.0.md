# Airalogy Platform v0.2.0

本版本新增可复现分析与受控 Workflow 编排，产品及所包含的 API、Web、Instrument Interface、Gateway、Compute Runner 统一到 0.2.0。

## 主要变化

- Protocol 卡片支持明确连线、固定版本、条件、审批以及声明的标量和文件输入，不依赖 AI。
- Record 与 Project 分析保留准确来源修订，区分证据综合和显式类型关联计算，支持方法保存、复用和不可变运行比较。
- 经过明确确认的方法可发布到 Workflow；支持的内置方法可形成普通可编辑 Protocol 草稿，独立审核后发布新版本。
- 显式选择的内置统计可沉淀为 Evidence 与经审核的 Knowledge，不会自动共享私有报告或源文件。
- AI 辅助保留明确同意与可编辑草稿；嵌入通过 Masterbrain 调用并保留关键词降级路径；本地与 CI 的 Node 工具和验证入口统一。
- Docker Protocol 执行明确提示缺失镜像与启动失败，不隐式拉取镜像，API 日志不再打印私有执行参数。

## 升级与恢复

目标数据库修订为 `0075_legacy_file_metadata`。历史源码部署不一定处于 v0.1.0 正式发布的数据库基线。先备份数据库、对象存储、配置、源码身份和前端资源，在隔离环境恢复并测试迁移，再停止生产写入、补做最终备份并切换。

已有文件但缺少存储元数据的早期数据库，必须明确指定核实过的原存储后端：`alembic -x legacy_storage_backend=oss upgrade head`（仅当原文件在 MinIO 时使用 `minio`）。缺少的旧版 Workflow 基础表会在科研任务迁移前补齐。文件迁移只增加元数据，不复制对象、不改变原对象路径，也不根据默认配置猜测原存储位置；降级保留新增字段，避免丢失文件位置。

`pg_dump` 必须兼容源 PostgreSQL 主版本。不得在应用升级时顺带将外部 PostgreSQL 17 替换成较旧的内置数据库。未另行批准迁移时，应保留已有数据库和对象存储地址。演练服务不得使用生产 AI、通知或设备凭据。

切换失败时使用旧应用及经过验证的备份恢复。基于备份恢复会丢失备份后的写入，因此验收通过前不要重新开放写入。阅读[部署身份说明](../release-and-deployment-identity.md)，核对正式发布清单和镜像摘要；仅有源码标签不等于部署验收通过。

## 能力边界

跨 Protocol 的 Aira 问答、可版本化单位转换/清洗与重复实验处理仍属后续工作。不包含任意 Compute 方法提升为普通 Protocol、任意 Compute 结果发布。计算以 Python 为主，已有可选 R 兼容不要求安装 R。真实仪器仍需独立现场验证；执行成功及组织审核不代表科学结论已被验证，也不代表实现完全自主科研。
